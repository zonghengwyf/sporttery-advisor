# 竞彩足球投注顾问 Constitution

## Core Principles

### 一、统计纪律高于情报直觉

任何投注方案的生成，MUST 以校准后的概率模型输出（Dixon-Coles + 市场融合）作为起点。
AI 情报分析和竞彩规则解读只能在统计框架内修正权重，MUST NOT 绕过统计层直接输出推荐方案。

引入新分析维度时，MUST 问：它是在修正统计先验，还是在替代统计先验？替代即违宪。

**为什么是宪法级别的**：中国市场不缺"专家推荐"，缺的是有统计纪律支撑的推荐。一旦允许
AI 绕过统计层直接出单，产品退化为另一个伪装成 AI 的主观推单软件，核心差异化消失。

### 二、透明度是唯一的信任货币

系统 MUST 对用户展示三件事：推荐的推理链（不只是结论）、真实历史回测指标（Brier /
Log-loss / RPS / ECE，MUST NOT 裁剪或美化亏损周期）、当前推荐的置信度与风险级别。

MUST NOT 只展示结论不展示依据。MUST NOT 隐藏或选择性呈现亏损区间的回测数据。

**为什么是宪法级别的**：用户购买的不只是推荐，而是做决策的依据。任何数据展示的选择性，
都会在用户亏钱后立刻摧毁信任。透明度也是产品合规边界的护城河——一旦妥协，产品从
"分析工具"滑向"诱导下注工具"，这是不可逾越的产品定义红线。

### 三、风控优先于收益最大化

Kelly 仓位管理是系统的默认且强制行为，MUST NOT 作为可选功能。任何票型方案 MUST 在
输出前经过资金分配校验。

M串N 容错方案的存在逻辑是分散风险而非放大收益——产品文案与 UI MUST 始终强调这一点。
MUST NOT 在界面上暗示"全押"或"重仓"。

**为什么是宪法级别的**：目标用户是普通彩票用户，极易被高赔率叙事吸引而超额下注。一次
连败摧毁整体体验，同时带来监管风险。留住用户长期使用比单次推动重仓重要得多。风控设计
是产品对用户的基本责任，也是商业可持续性的前提。

### 四、竞彩规则知识是产品的专业护城河

产品 MUST 深度编码中国竞彩的特有规则知识：控分识别、赛季末激励分析、异常让球线、SP
基线对标。这些知识 MUST 系统性地注入分析流程，MUST NOT 依赖通用 LLM 的泛化理解。

每次引入新的外部 AI 模型，竞彩规则知识注入 MUST 重新验证有效性。

**为什么是宪法级别的**：竞彩有独特的市场结构（彩民资金池、SP 机制、官方赔率设计逻辑），
这些知识不在任何 LLM 的训练数据里，或即便有也是碎片化的。放弃它就等于放弃专业定位，
变成一个披着中国皮的通用体育预测工具。

### 五、移动场景下核心信息一屏可见

产品主要使用场景是用户在开奖前几小时内，用手机快速查看并决策。所有核心决策信息（推荐
方案、置信度、风险级别、预计赔率）MUST 在手机屏幕无需横屏、无需缩放的情况下一屏可见。

需要深度阅读才能理解的信息，MUST 在视觉层级上明确降权。
MUST NOT 用"Data-Dense Dashboard"为过度复杂的信息展示辩护。

**为什么是宪法级别的**：这条原则约束的不只是 UI，而是信息架构的优先级排列。中国彩民的
购彩行为高度时间敏感，决策窗口短、场景嘈杂。要求用户"仔细研究"才能使用的产品，在真
实场景下是失败的，无论统计模型多精确。

### 六、系统可用性不绑定单一外部依赖

每类核心数据（赛单、赔率、赛果、历史战绩）MUST 有可自动触发的降级路径。降级触发与恢复
MUST 自动完成，MUST NOT 依赖人工干预。

产品核心功能（查看推荐方案、查看历史回测）在任意单一外部 API 失效时 MUST 保持可用，
即便数据时效有所降低。

**为什么是宪法级别的**：产品价值在开奖前窗口期高度集中，此时任何外部 API 失效对用户
信任的伤害是指数级的。竞彩官方 API 的稳定性不受产品方控制——这是已知外部风险，MUST
从架构原则层面而非临时补丁层面解决。

## 技术栈约束

任何技术引入或替换 MUST 满足以下约束：

| 层 | 约束 |
|---|---|
| 前端 | Vue 3 + Vite + Tailwind CSS + Pinia，MUST NOT 引入 React/Angular |
| 后端 | FastAPI (Python 3.11+)，异步优先（async/await） |
| 主数据库 | PostgreSQL，通过 `get_db()` AsyncSession 访问 |
| 快照存储 | DuckDB 仅用于预测历史和回测结果，MUST NOT 存用户数据 |
| LLM | 所有模型通过统一客户端调用，MUST 使用 OpenAI 兼容层适配中国模型 |
| 调度 | APScheduler，MUST 从 DB 读取配置，MUST NOT 硬编码调度参数 |

## 开发工作流

### Skill 路由规则

功能开发 MUST 遵守以下路由：

- **UI 改动** → `/design-taste-frontend` 确认风格 → `/frontend-ui-engineering` 实现
- **新功能** → `/grill-me` 需求对齐 → `/speckit-specify` → `/speckit-tasks` → 实现
- **多文件改动** → `/incremental-implementation`
- **Bug** → `/diagnosing-bugs`（reproduce → minimize → fix → regression-test）
- **合并前** → `/code-review`（Standards + Spec 双轴）

### 验收门槛

所有验收 MUST 在真实 Docker 环境中进行，MUST NOT 仅依赖单元测试替代集成验证。

## Governance

此宪法超越 CLAUDE.md 中所有其他约定。原则冲突时以本文件为准。

**修改流程**：
1. 原则级变更 MUST 创建 ADR（`docs/adr/`）记录决策依据
2. 版本递增：MAJOR（原则删除/重定义）/ MINOR（新原则/章节）/ PATCH（措辞/拼写）
3. 修改后运行 `/speckit-constitution` 更新本文件并更新 `LAST_AMENDED_DATE`

运行时开发指导见 `CLAUDE.md`。领域词汇表见 `CONTEXT.md`（由 `/grill-with-docs` 维护）。
工程实现约定（时区、降级链细节、UI 像素规范）见 `CLAUDE.md` 开发规范章节。
